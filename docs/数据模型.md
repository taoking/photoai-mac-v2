# 数据模型

> 状态：v1.0（2026-11-19）。产品规则已与用户确认（见[设计稿](设计稿.md) v1.3）；表结构是 M1 的实现起点，实现中可以调整，但每次调整都要同步本文件，并补上对应的测试。产品规则见 [产品定位与目标](产品定位与目标.md)。

## 1. 总体

- 一个 SQLite 数据库：`~/Library/Application Support/PhotoAI-Mac-v2/library.sqlite`，WAL 模式。
- 预览文件：`~/Library/Application Support/PhotoAI-Mac-v2/Previews/<photo_id 前两位>/<photo_id>-480.jpg` 与 `-1600.jpg`，按照片存，不按卷存。
- 软件和命令行工具共用同一个数据库和同一套读写代码。
- **不开 App 沙盒。** 只给自己用，不上架；不开沙盒就能直接访问 `/Volumes` 下的任何卷，省掉 v1 的 security-scoped bookmark 和重新定位整套机制。

## 2. 实体关系

```text
volumes 1 ─── n locations n ─── 1 files n ─── 1 photos
   │                                            │
   └── n scan_dirs          collection_members n┤
                            faces n ────────────┤
                            ocr (1:1) ──────────┘
```

- **photo**：一次拍摄。评分、标记、收藏夹、人物、OCR、预览都挂在这里。
- **file**：照片的一个格式成员，比如同一张照片的 ARW 和 JPG 是两个 file。**副本、清卡、导出都按 file 计算。**
- **location**：某个 file 在某个卷上的一份副本。
- **scan_dir**：某个卷上的一个目录最近一次是否完整扫完。

## 3. 表

### volumes

| 列 | 说明 |
| --- | --- |
| `id` | 主键 |
| `volume_uuid` | 系统卷 UUID，用来认卡 |
| `name` | 用户起的名字 |
| `scan_root` | 扫描的文件夹，相对卷根目录；存储卡默认 `DCIM`，外置盘添加时手动选 |
| `capacity_bytes`、`filesystem` | 展示用 |
| `status` | `active` / `removed` |
| `removed_at` | 移除时间 |
| `last_seen_at`、`last_scanned_at` | 最后在线、最后一次完整扫完的时间 |

“在线 / 离线”是运行时状态，由当前挂载的卷决定，不入库：启动时列一次已挂载的卷（`FileManager.mountedVolumeURLs` + 卷 UUID），之后靠 `NSWorkspace` 的挂载 / 卸载通知更新，开销只和卷的数量有关。不逐个检查原片。

原片是否还在，只在三个时机确认：扫描（含已知卷插上时的自动重扫）、读原片（导出、100% 放大、补副本）、清卡检查核对副本。读不到时把对应 location 改为 `historical`，并在同一个事务里更新 `present_location_count`。**不监听文件系统变动（不用 FSEvents），也不定期主动扫描**（用户已确认）。已移除的卷重新插上时建一条新记录，不复活旧记录。

### photos

| 列 | 说明 |
| --- | --- |
| `id` | 主键 |
| `identity_key` | 身份，见 §4，唯一索引 |
| `base_name` | 去掉扩展名的文件名，如 `DSC01926` |
| `file_number` | 从文件名提取的数字编号，如 `1926`，命令行按编号匹配用 |
| `capture_date` | 拍摄时间，精确到秒（身份用） |
| `capture_subsec` | 亚秒，只用于排序，不参与身份 |
| `camera_make`、`camera_model`、`lens`、`focal_length`、`aperture`、`shutter`、`iso`、`width`、`height` | 元数据 |
| `latitude`、`longitude`、`geo_cell`、`place_id` | 地点 |
| `rating` | 0–5 |
| `flag` | `none` / `pick` / `reject` |
| `preview_file_id` | 用哪个 file 生成预览（优先 JPEG） |
| `thumb_state`、`preview_state` | 480 / 1600 两档预览：`pending` / `ready` / `failed`。`ready` 表示文件已写完并能解码 |
| `ocr_state`、`face_state` | 后台任务状态 |
| `present_location_count` | 现存位置数，冗余字段，见 §6 |
| `imported_at`、`import_batch_id` | 导入时间与批次 |

### files

| 列 | 说明 |
| --- | --- |
| `id`、`photo_id` | |
| `extension`、`kind` | `raw` / `jpeg` / `heif` / … |
| `file_size` | 字节数，以第一次收录时为准 |

`(photo_id, extension)` 唯一。

### locations

| 列 | 说明 |
| --- | --- |
| `id`、`file_id`、`volume_id` | |
| `relative_path` | 相对卷根目录 |
| `dir_path` | 所在目录（相对卷根目录），用来判断这个目录是否扫完 |
| `file_size` | 这份副本的大小；与 `files.file_size` 不同时不算有效副本 |
| `file_mtime` | 只用来跳过未变文件，不参与身份 |
| `status` | `present` / `historical` |
| `last_seen_at` | 最后一次确认文件还在的时间 |

唯一约束只加在现存位置上：`UNIQUE(volume_id, relative_path) WHERE status = 'present'`。同一路径可以有多条历史位置，对应先后放过的不同照片。

### scan_dirs

| 列 | 说明 |
| --- | --- |
| `volume_id`、`dir_path` | 主键 |
| `state` | `complete` / `incomplete` |
| `last_complete_at` | 最后一次完整列出的时间 |
| `last_error` | 没扫完的原因（拔卡、取消、权限、读写错误） |

### 其他

- `collections(id, name, created_at, last_used_at)`；`collection_members(collection_id, photo_id, added_at)`。
- `labels(id, name, color, sort_order)`：用户定义的标签，`sort_order` 决定快捷键；`photo_labels(photo_id, label_id)`：一张照片可以有多个标签。
- `people(id, name, is_hidden)`；`faces(id, photo_id, person_id, bbox, feature)`。
- `ocr_text`：FTS5 全文索引，和文件名一起建，供搜索使用（需确认系统自带 SQLite 已启用 FTS5）。
- `places(geo_cell, name, source, fetched_at)`：地名缓存，一个约 1 公里的网格一行。
- `import_batches(id, volume_id, started_at, finished_at, photo_count)`：“最近导入”。

## 4. 照片身份

**名字不同，一定不是同一张。** 名字相同时，再看拍摄时间：

```text
identity_key = base_name + 拍摄时间（精确到秒）
没有拍摄时间时 = base_name + 文件大小
```

- `base_name` 是去掉扩展名的文件名，只统一大小写，不做其他改写。`DSC01926 (1)` 和 `DSC01926` 是两张不同的照片。
- **不用亚秒。** RAW 和 JPEG 可能一个带亚秒、一个不带，带上会让同一次拍摄合不成一组；同一秒内的连拍文件名本来就不同，不需要亚秒来区分。
- 同一 `identity_key` 下的 ARW 和 JPG 自动成为同一张照片的两个 file。
- 没有拍摄时间时按大小兜底，RAW 和 JPEG 大小不同，不会合组。这种情况在相机照片里很少见，接受；M1 用真实 RAW + JPEG 样片记录 EXIF 原始字段和实际合组结果，证据不足时宁可不合组，不用编号强行合组。
- 不默认计算文件哈希：读完整文件太慢（一张 ARW 约 35 MB，卡上 1,800 张就是 60 GB 的读取量），而拍摄时间在读 EXIF 时已经拿到了。哈希只在补副本时用来校验复制结果。
- 不比较修改时间。
- 编号循环后，同编号的不同照片拍摄时间不同，不会合在一起。

## 5. 扫描

按目录进行。每个目录：

1. **列出目录内容。** 列不完（拔卡、取消、权限、读写错误）就把这个目录记为 `incomplete`，跳过第 4 步，保留上次结果，下次插上时续扫。
2. **逐个文件处理：**
   - 同路径有现存位置，且大小、修改时间都没变：只更新 `last_seen_at`。
   - 同路径只有历史位置，或大小、修改时间变了：读 EXIF 算身份。
     - 身份与这个路径上原来的文件相同：恢复为现存或更新大小、时间。**历史位置重新出现必须恢复，不能因为大小、时间没变而跳过。**
     - 身份不同（同一路径换了照片）：旧位置改为历史；新文件挂到自己身份对应的照片上（已有就加位置，没有就新建照片），新照片不继承旧照片的评分。
   - 新路径：读 EXIF 算身份，加位置。
3. **按批提交事务**，同一事务里更新 `present_location_count`，网格边扫边出现。
4. **目录完整列出后**，这个目录里本次没见到的现存位置改为历史；上次存在、这次在完整列出的父目录里已经不见的子目录，其下的现存位置也改为历史。目录记为 `complete`。

整卷扫完（所有目录都是 `complete`）才更新 `volumes.last_scanned_at`。

## 6. 可见性

照片可见 ⇔ 至少有一个 location 满足 `status = present` 且所属卷 `status = active`。

为了让 10 万张的网格查询不必每次联表计数，`photos.present_location_count` 作为冗余字段，在下面几种情况下于同一个事务里更新：

- 新增或恢复 location；
- location 变为 historical（扫描、读原片失败、清卡核对、同路径换片）；
- 卷被移除。

常规列表、搜索、收藏夹、命令行一律加 `present_location_count > 0`；“无卷关联照片”界面查 `= 0`。在这个界面确认删除时，在删除事务里重新检查 `present_location_count = 0`，期间被重扫找回的照片不删。

## 7. 清卡与补副本

对卡上每个现存 location 对应的 file，找它在其他卷上的现存 location（`file_size` 一致才算）：

| 结果 | 条件 |
| --- | --- |
| 已核实 | 至少一份副本在在线卷上，并且当场 `stat` 确认文件还在、大小一致 |
| 只有离线记录 | 没有已核实的副本，但有副本在离线卷上 |
| 缺副本 | 别处没有现存副本；当场核对发现不在的副本顺手改为历史 |

“可以清空”⇔ 所有 file 都是“已核实”，且这张卡上所有照片的 `thumb_state`、`preview_state` 都是 `ready`。

补副本：

- 只复制“缺副本”的 file；保留原文件名，同一张照片的 file 放在同一目录。
- 目标目录已有同名文件时，整组换到新的子目录（如 `补副本-2026-11-19/`），不改文件名，不动目标上已有的文件。
- 复制时算源文件 SHA-256，写完读回目标再算一次，相同才算成功；然后按 §5 扫描目标目录登记副本。
- 源文件读不到、目标写满、校验不一致的 file 单独报告，不登记位置。

## 8. 写入规则

- 按字段更新，例如 `UPDATE photos SET rating = ? WHERE id IN (…)`，不整行覆盖。
- 涉及多张表的操作（移除卷、扫描批次、删除无卷关联照片）放在一个事务里，失败整体回滚，界面报错，内存状态不变。
- 写入失败不能悄悄丢掉。v1 的后台写入出错只留一条提示，那批改动就没了。
- 预览文件写在库外：先写临时文件、能解码后改名，再在事务里把对应状态改为 `ready`。启动时发现状态是 `ready` 但文件缺失或解码失败的，改回 `pending` 重做。
- 软件窗口重新获得焦点时读 `PRAGMA data_version`，变了才重读受影响的数据。
- 两边都设置 `busy_timeout`，短暂锁定时等待重试。

## 9. 项目结构（建议）

```text
PhotoAICore      数据库、身份规则、扫描、预览生成、编号匹配；不依赖 SwiftUI
PhotoAIApp       SwiftUI 界面，@Observable 模型
photoai          命令行工具：rate、collect、find
```

命令行和软件共用 `PhotoAICore`，匹配规则（例如“编号命中多张取最晚”）只写一份。
